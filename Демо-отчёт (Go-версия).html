1Причины замедления работы

Критично Нехватка памяти для буферного кэша (или лишние чтения с диска)

Наблюдения:
  • PLE: мин 112, среднее 1709 сек (низкие значения = сброс кэша)
  • Доля ожиданий чтения с диска (PAGEIOLATCH и др.): 23%
  • Чтений с диска в среднем: 238.1 стр/сек

Данные не помещаются в буферный пул: SQL Server постоянно читает страницы с диска. Либо памяти мало, либо запросы читают слишком много лишнего (сканирования, отсутствующие индексы).

Что делать:
  • Проверить/увеличить max server memory и объём ОЗУ сервера.
  • Создать недостающие индексы, устранить сканирования больших таблиц.
  • Проверить задержки чтения по файлам (раздел «Диски и файлы»).

Важно Процессор перегружен

Наблюдения:
  • Средняя загрузка ЦП SQL: 37.5%, пиковая: 97%
  • Доля ожиданий ЦП/параллелизма: 33% от всех ожиданий
  • Самый дорогой запрос: 0 мс ЦП в среднем (SalesDb)

SQL Server не хватает вычислительных ресурсов: запросы стоят в очереди на планировщики, растут ожидания SOS_SCHEDULER_YIELD/CXPACKET.

Что делать:
  • Оптимизировать топ-запросы по ЦП (раздел «Топ запросов»).
  • Настроить cost threshold for parallelism (25–50) и MAXDOP осознанно: CXPACKET — не ошибка, а показатель параллельных запросов; с SQL Server 2016 SP2 безвредная часть вынесена в CXCONSUMER. Выключение параллелизма целиком (MAXDOP = 1) лишает тяжёлые отчёты ускорения — подбирайте значения по наблюдениям. Ориентир: ERP с тяжёлыми отчётами выигрывает от параллелизма, кусту бухгалтерских баз он нужен реже.

Важно Медленная запись журнала транзакций

Наблюдения:
  • Доля WRITELOG и связанных ожиданий: 14%
  • Средняя задержка записи журнала: до 28 мс (норма < 10–15 мс)

Диск не успевает фиксировать транзакции — все записи в БД замедляются (ожидания WRITELOG).

Что делать:
  • Перенести .ldf на более быстрый диск (SSD/NVMe), отдельно от данных.
  • Проверить частые мелкие autogrowth журнала.
  • Сократить объём/длительность транзакций приложения.

Важно Блокировки между транзакциями

Наблюдения:
  • Заблокированные процессы наблюдались в 39 замерах (максимум 11)
  • Доля ожиданий блокировок (LCK_M_*): 7%

Одни транзакции удерживают блокировки, другие ждут. Обычно виновата длинная транзакция (head blocker) или сканирования, захватывающие множество строк. Море LCK_M_* в ожиданиях — признак конкуренции за строки, а не «ошибка»: смотрите режим блокировок конфигурации 1С и длину транзакций.

Что делать:
  • Найти head-blocker в разделе «Блокировки» и оптимизировать его транзакцию.
  • Сократить длительность транзакций в приложении (коммитить чаще).
  • Оптимизировать запросы-жертвы (индексы).
  • Включить READ_COMMITTED_SNAPSHOT (RCSI) на OLTP-базах: читатели перестанут ждать писателей. Для баз 1С в управляемом режиме блокировок платформа включает RCSI сама.
  • Внимание: у баз 1С со старым режимом совместимости (автоматический/смешанный режим блокировок) транзакции идут на Repeatable Read/Serializable — RCSI на них не действует. Сначала перевод конфигурации на управляемый режим блокировок (БлокировкаДанных в коде), потом уровень изоляции, и только затем флаг RCSI.

2Рекомендации по устранению и оптимизации

Критично Включён AUTO_SHRINK: ReportsDb

Область: Базы данных

Проблема: Автосжатие файлов вызывает постоянное уменьшение/рост файлов, фрагментацию и нагрузку на ЦП — одна из самых вредных настроек.

Рекомендация: Отключите AUTO_SHRINK и управляйте размером файлов вручную.

Показать SQL-скрипт исправления
ALTER DATABASE [ReportsDb] SET AUTO_SHRINK OFF;

Критично Нет полной резервной копии за последние 7 дней: ReportsDb, Legacy2014

Область: Резервное копирование

Проблема: Восстановление после сбоя будет невозможно. Проверьте задания резервного копирования.

Рекомендация: Настройте регулярное резервное копирование (полное — еженедельно/ежедневно, разностное — ежедневно, журнал — каждые 15–30 минут для FULL-модели).

Показать SQL-скрипт исправления
BACKUP DATABASE [ReportsDb] TO DISK = N'D:\Backup\ReportsDb.bak' WITH COMPRESSION, INIT, CHECKSUM;
BACKUP DATABASE [Legacy2014] TO DISK = N'D:\Backup\Legacy2014.bak' WITH COMPRESSION, INIT, CHECKSUM;

Критично FULL-модель без копий журнала: SalesDb, Legacy2014

Область: Резервное копирование

Проблема: Журнал транзакций растёт бесконечно (log_reuse_wait = LOG_BACKUP). Возможны переполнение диска и потеря данных на точку отказа.

Рекомендация: Настройте регулярное резервное копирование журнала транзакций.

Показать SQL-скрипт исправления
BACKUP LOG [SalesDb] TO DISK = N'D:\Backup\SalesDb_log.trn' WITH COMPRESSION, INIT;
BACKUP LOG [Legacy2014] TO DISK = N'D:\Backup\Legacy2014_log.trn' WITH COMPRESSION, INIT;

Важно Включён AUTO_CLOSE: StatsDb

Область: Базы данных

Проблема: База закрывается после отключения последнего пользователя: каждый новый коннект платит за открытие файлов и очистку кэша процедур.

Рекомендация: Отключите AUTO_CLOSE.

Показать SQL-скрипт исправления
ALTER DATABASE [StatsDb] SET AUTO_CLOSE OFF;

Важно CHECKSUM отключён: Legacy2014

Область: Базы данных

Проблема: Без CHECKSUM повреждения страниц могут оставаться незамеченными до резервного копирования (когда уже поздно).

Рекомендация: Включите проверку страниц и пересоздайте бэкапы.

Показать SQL-скрипт исправления
ALTER DATABASE [Legacy2014] SET PAGE_VERIFY CHECKSUM;

Важно Неоптимальный autogrowth файлов

Область: Базы данных

Проблема: SalesDb!SalesDb_data01: шаг 2 МБ; SalesDb!SalesDb_log: рост 10%; ReportsDb!ReportsDb_data: шаг 1 МБ; StatsDb!StatsDb_data: шаг 0 МБ

Рекомендация: Процентный рост на больших файлах приводит к длительным паузам и фрагментации; мелкий шаг (1–64 МБ) у больших файлов вызывает тысячи расширений. Задайте фиксированный шаг 256–512 МБ (данные) / 512–1024 МБ (журнал) и следите за свободным местом.

Важно Слишком много VLF в журнале транзакций

Область: Базы данных

Проблема: SalesDb: 1184 VLF

Рекомендация: Больше 1000 виртуальных файлов журнала замедляют восстановление и операции с журналом (crash recovery, log reader).

Показать SQL-скрипт исправления
Уменьшите журнал до минимума и заново увеличьте крупными порциями (ALTER DATABASE ... MODIFY FILE (SIZE=...)).

Важно Непрямой checkpoint выключен (target_recovery_time = 0)

Область: Базы данных

Проблема: Базы: SalesDb, ReportsDb, StatsDb. База, развёрнутая со старой версии SQL Server, сохраняет автоматический checkpoint со всплесками записи; с 2016 новые базы создаются с непрямым checkpoint и целевым временем восстановления 60 секунд, запись идёт ровным фоном. Эффект заметнее всего на машинах с большой памятью.

Рекомендация: Включите непрямой checkpoint: ALTER DATABASE ... SET TARGET_RECOVERY_TIME = 60 SECONDS (для крупных баз — 60–120 с; учитывайте, что растёт нагрузка фоновой записи).

Показать SQL-скрипт исправления
ALTER DATABASE [SalesDb] SET TARGET_RECOVERY_TIME = 60 SECONDS;
ALTER DATABASE [ReportsDb] SET TARGET_RECOVERY_TIME = 60 SECONDS;
ALTER DATABASE [StatsDb] SET TARGET_RECOVERY_TIME = 60 SECONDS;

Важно Журнал транзакций не может усечься

Область: Базы данных

Проблема: SalesDb — не сделана копия журнала. Пока причина не устранена, журнал растёт и может занять том (аварийный сценарий «журнал переполнен»).

Рекомендация: Устраните причину: настройте копии журнала для FULL-модели, не держите длинные транзакции, проверьте репликацию/агентов. Не используйте shrink как решение — рвётся цепочка восстановления.

Важно Смешанная аутентификация и учётные записи с полными правами

Область: Безопасность

Проблема: Сервер разрешает SQL-аутентификацию; SQL-логинов: 4, из них с правами sysadmin: 2. Привилегированные логины: 1C_Admin, report_svc. Схема «везде sa, под ним всё работает» — открытая дыра: пароль известен неопределённому кругу лиц и годами не меняется, а ротация служебных учёток даётся тяжелее всего.

Рекомендация: Службы и подключение сервера приложений 1С — под доменными учётки (вершина — gMSA: пароль генерирует и ротирует домен), доступ к СУБД — Windows-аутентификация, права выдаются под задачу. Отключите sa и удалите ненужные SQL-логины.

Показать SQL-скрипт исправления
ALTER LOGIN [sa] DISABLE;
-- проверить привилегированных:
SELECT p.name, p.type_desc FROM sys.server_principals p
  WHERE IS_SRVROLEMEMBER('sysadmin', p.name) = 1;

Важно Instant File Initialization отключён

Область: Конфигурация ОС

Проблема: Службы: SQL Server (PROD). Без этого права файлы данных растут и восстанавливаются из копии с предварительным заполнением нулями — на больших базах это часы лишнего времени.

Важно План электропитания Windows — «Сбалансированный»

Рекомендуется Не включён READ_COMMITTED_SNAPSHOT (RCSI)

Область: 1С

Проблема: Базы без RCSI: SalesDb, ReportsDb, StatsDb, Legacy2014. По умолчанию SQL Server работает в READ COMMITTED с блокировками: читающий запрос ждёт пишущую транзакцию и наоборот. С RCSI включается версионирование строк — читатели получают снимок данных и не блокируют друг друга. Именно поэтому тест «на PostgreSQL 1С не тормозит» сравнивает не СУБД, а две модели изоляции. Внимание: у баз ReportsDb (compat 110), Legacy2014 (compat 100) старый режим совместимости 1С — платформа поднимает уровень изоляции до Repeatable Read/Serializable, и RCSI на такие транзакции не действует (флаг меняет только READ COMMITTED). Типичный случай: включили RCSI, а LCK_M_* остались.

Рекомендация: Включите RCSI на OLTP-базах: ALTER DATABASE [<база>] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE (нужно окно: возможны ожидания). Следите за tempdb: хранилище версий строк живёт в tempdb; одна длинная транзакция не даёт его чистить — версии копятся и tempdb растёт. Для легаси-конфигураций 1С сначала перевод на управляемый режим блокировок (расставить БлокировкаДанных в коде!), затем уровень изоляции, и только потом RCSI. Для 1С 8.3 в управляемом режиме (снят режим совместимости с 8.2) платформа включает RCSI сама.

Показать SQL-скрипт исправления
ALTER DATABASE [SalesDb] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;
ALTER DATABASE [ReportsDb] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;
ALTER DATABASE [StatsDb] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;
ALTER DATABASE [Legacy2014] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;

Рекомендуется Службы SQL Server работают под локальными учётными записями

Область: Безопасность

Проблема: SQL Server (PROD) — NT AUTHORITY\SYSTEM; SQL Server Agent (PROD) — NT AUTHORITY\SYSTEM. По методике службы сервера СУБД и сервера приложений 1С работают под доменными учётными записями; вершина схемы — групповые управляемые учётные записи служб (gMSA): пароль генерирует и ротирует домен, его не знает ни один сотрудник.

Рекомендация: Переведите службы на доменные учётные записи, подключение к СУБД — на Windows-аутентификацию, права выдавайте под задачу (вместо sysadmin «чтобы работало»).

Рекомендуется Включены именованные каналы

Область: Безопасность

Проблема: Именованные каналы нужны не всегда; лишний протокол — лишняя поверхность атаки (в методике — оставить TCP/IP).

Рекомендация: Отключите именованные каналы, если под них ничего не написано. Проверьте также правило брандмауэра: порт 1433 разрешается не «из локальной сети», а только с адреса сервера приложений 1С; SQL Browser выключается, порт инстанса задаётся статически; RDP наружу не публикуется (VPN).

Рекомендуется Сервер — виртуальная машина: проверьте настройки гипервизора

Область: Виртуализация

Проблема: Тип: HYPERVISOR. Сокетов: 2, ядер на сокет: 8, NUMA-узлов: 2. Изнутри гостя половина проблем не видна: диспетчер задач показывает свободный процессор, а запросы выполняются медленно.

Рекомендация: Память продуктивной ВМ резервируется в полном объёме (VMware memory reservation; в Hyper-V — отключить Dynamic Memory и задать статический объём): ballooning вытесняет буферный пул, PLE обваливается без видимых причин. Переподписка vCPU держится близко к 1:1, CPU Ready ≤ 5%; ядра «про запас» не раздаются — 8 vCPU нередко работают быстрее 24. Проверьте vNUMA (в vSphere до 8.0 горячее добавление CPU отключает vNUMA), паравиртуальный контроллер PVSCSI и раздельные виртуальные контроллеры для данных, журналов и tempdb. Снапшоты долго не хранить (растут и замедляют запись; stun при создании/удалении даёт регулярные подвисания по расписанию бэкапа). Датастор не должен быть общим с соседними ВМ, отбирающими IOPS.

Рекомендуется Lock Pages in Memory не включён

Область: Конфигурация

Проблема: На сервере 64 ГБ ОЗУ рекомендуется разрешить SQL Server фиксировать страницы в памяти (защита от вытеснения ОС).

Рекомендация: Выдайте учётной записи служб SQL Server право «Lock pages in memory» (групповая политика) и перезапустите службу.

Рекомендуется Query Store не включён на части баз

Область: Мониторинг

Проблема: Базы: StatsDb, Legacy2014. С 2017 Query Store хранит и статистику ожиданий в привязке к конкретным запросам, с 2022 включён по умолчанию для новых баз; база, восстановленная со старой версии, сохраняет прежние настройки — включать нужно вручную. Рекомендация: Включите и настройте Query Store на продуктивных базах; мониторинг имеет смысл только тогда, когда есть кому читать метрики (штатный DBA или внешний специалист на сопровождении).

Как формируется отчёт. Данные собираются из системных динамических представлений SQL Server:
sys.dm_os_performance_counters (счётчики), sys.dm_os_wait_stats (ожидания), sys.dm_exec_requests /
sys.dm_exec_sessions (активные запросы и блокировки), sys.dm_io_virtual_file_stats (ввод-вывод файлов),
sys.dm_os_sys_info и sys.dm_os_sys_memory (ЦП и память), sys.configurations (настройки),
sys.databases и msdb.dbo.backupset (базы и копии), sys.dm_exec_query_stats (топ запросов),
sys.dm_db_missing_index_* (недостающие индексы), sys.dm_db_index_physical_stats (фрагментация).


Методология. Анализ причин замедления основан на методологии ожиданий (waits-and-queues):
нерабочие ожидания отфильтрованы, остальные сгруппированы по категориям (ЦП, память, диск, блокировки,
сеть), и по их долям в сочетании со счётчиками (PLE, ЦП, задержки файлов) определяются узкие места.


Важно. Рекомендации — отправная точка для оптимизации. Перед применением скриптов
(особенно CREATE INDEX, ALTER DATABASE, sp_configure) проверяйте их на тестовой среде и учитывайте
особенности вашей нагрузки. Для полного мониторинга учётной записи нужны права VIEW SERVER STATE
и чтение msdb.


Суточный мониторинг. Программа опрашивает сервер каждые 30 секунд (настраивается) и хранит
историю до 7 дней; отчёт можно сформировать в любой момент — графики строятся за последние 24 часа.


Методика настройки. Расширенные проверки (коллация, Instant File Initialization, план
электропитания, разнесение файлов по томам, свободное место, tempdb, непрямой checkpoint, RCSI/ADR,
Query Store, размещение и шифрование копий, режим аутентификации и учётные записи служб) построены по
