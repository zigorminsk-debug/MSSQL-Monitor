**Объект аудита:** экземпляр `SQLSRV-PROD-01\PROD` (данные суточного мониторинга и полного снимка,

## 2. Память

**Несоответствие:** `max server memory = 2147483647` (без лимита), ОС свободно ~2,8 ГБ из 64 ГБ;
PLE проседает до 90 с, есть Memory Grants Pending, доля PAGEIOLATCH 23 % — SQL Server читает с диска
то, что должно лежать в кэше.

**Как по статье** (ч. 1): при установке оставлять ОС запас: на 8 ядрах/32 ГБ — не меньше 6 ГБ;
на крупных инстансах 12–15 ГБ; в кейсе 144 ядра/1,5 ТБ ОЗУ под ОС отдают до 20 ГБ. Правило простое:
max server memory задаётся сразу при инсталляции, а не «потом».

**Действие:** ограничить буферный пул, оставив ОС ~9–10 ГБ (16 ядер, 64 ГБ, базы 266 ГБ — кэша всё
равно не хватит на всё, поэтому важнее предсказуемость):

```sql
EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'max server memory (MB)', 55680; RECONFIGURE;   -- ≈ 9,6 ГБ остаётся ОС
```

Дополнительно:
- право **Lock Pages in Memory** для служебной учётки (крупный сервер) — `secpol.msc` →
  «Локальные политики» → «Назначение прав пользователя» → «Блокировка страниц в памяти», затем
  перезапуск службы SQL Server;
- после настройки следить за показателями: PLE, Memory Grants Pending, «Свободная память ОС» —
  при стабильном дефиците решать вопрос о добавлении ОЗУ (ст. 1: сначала диагностика, потом железо).

## 3. Параллелизм (MAXDOP и cost threshold)

**Несоответствие:** `MAXDOP = 0` (все 16 ядер), `cost threshold = 5` (дефолт ещё с 2005 г.),
доля ожиданий семейства CXPACKET — 33 % от всех ожиданий.

**Как по статье** (ч. 2): рекомендация «MAXDOP = 1» из старой методики 1С — ошибочна, тяжёлая ERP
выигрывает от параллелизма; `cost threshold = 5` — легаси, ставить 25–50. Значения индивидуальны и
подбираются по наблюдениям 2–3 месяца. CXPACKET (с 2016 SP2 — безвредная часть в CXCONSUMER) — не
«ошибка», а индикатор параллельных запросов.

```sql
EXEC sp_configure 'max degree of parallelism', 8;  RECONFIGURE;   -- 16 ядер → 8
EXEC sp_configure 'cost threshold for parallelism', 40; RECONFIGURE; -- 25–50
```

Контроль: после изменения сравнить по отчёту доли `CXPACKET/CXCONSUMER`, `SOS_SCHEDULER_YIELD`
и пиковую загрузку ЦП через 2–4 недели (цель статьи — средняя загрузка ЦП ≤ 40 %).

## 4. tempdb

**Несоответствия:** один файл данных (`tempdev`, 8 ГБ), рост 10 %; tempdb лежит на `D:` вместе с
данными; tempdb — «хранилище версий строк» (ст. 2), а значит самый нагруженный на запись объект.

**Как по статье** (ч. 2): файлов данных — по числу логических ядер (при ≥ 8 достаточно 8), все
одинакового размера, одинаковый **фиксированный** шаг роста, предварительная аллокация. (ч. 1):
tempdb — на отдельный том, обязательно на RAID, под версии строк.

## 5. Файлы и тома

**Несоответствия:** данные и tempdb на одном томе `D:`; на `D:` свободно 42 ГБ (10,5 %);
авторост 1–2 МБ на данных и 10 % на журнале; журнал SalesDb — 1184 VLF; средняя задержка записи
журнала до 29 мс (норма < 10–15 мс); один data-файл на базу.

**Как по статьям:** (ч. 1) C = ОС, D = mdf, E = ldf, F = tempdb, бэкапы — на сетевой ресурс;
RAID/быстрые накопители под tempdb; NVMe — write-intensive модели; кластер томов 64 КБ;
преаллокация + крупный autogrowth (мелкий шаг — тысячи расширений и фрагментация).
(ч. 2) Диск журнала — первое, что смотрят при WRITELOG.

**Действия:**

1) Крупный фиксированный шаг роста (вместо 10 % и 1–2 МБ):

```sql
ALTER DATABASE [SalesDb] MODIFY FILE (NAME = N'SalesDb_data01', FILEGROWTH = 512MB);
ALTER DATABASE [SalesDb] MODIFY FILE (NAME = N'SalesDb_log',    FILEGROWTH = 1024MB);
ALTER DATABASE [ReportsDb] MODIFY FILE (NAME = N'ReportsDb_data', FILEGROWTH = 512MB);
-- журнал одной крупной порцией не «процент», а фиксированные 512–1024 МБ
```

2) Пересоздать журнал SalesDb (устранить 1184 VLF) — в окно обслуживания, после того как налажены
   копии журнала:

```sql
USE [SalesDb];
CHECKPOINT;
BACKUP LOG [SalesDb] TO DISK = N'D:\Backup\SalesDb_log.trn' WITH COMPRESSION, INIT;
-- временно уменьшить (журнал пуст) и вырастить ОДНИМ крупным шагом:
DBCC SHRINKFILE (N'SalesDb_log', 1024);
ALTER DATABASE [SalesDb] MODIFY FILE (NAME = N'SalesDb_log', SIZE = 16384MB);
```

3) Разнести потоки по томам (ч. 1: C/D/E/F) и освободить место: перенести отдельные файлы
   (`ALTER DATABASE ... MODIFY FILE (FILENAME = ...)` + `WITH OFFLINE`), вынести tempdb на `F:`,
   держать на томах данных ≥ 15 % свободного места. Целевая конфигурация «под себя» — как в статье:
   данные/журналы/tempdb на разных томах (или хотя бы данных и журналов — физически разных дисках).

4) Прогнать DiskSpd и сохранить эталон (ч. 1): цифры нужны при приёмке железа и для сравнения
   при подозрении на деградацию.

```
diskspd -c10G -d120 -w25 -b64K -t8 -o32 -L D:\diskspd-test.dat
```

## 7. Checkpoint (непрямой)

**Несоответствие:** `sys.databases.target_recovery_time_in_seconds = 0` у всех пользовательских баз
(SalesDb, ReportsDb, StatsDb, Legacy2014). У `master` — 60.

**Как по статье** (ч. 2): старые базы, развёрнутые до 2016, живут с автоматическим checkpoint; он
пишет «всплесками» и на серверах с большой памятью даёт заметные задержки. Непрямой checkpoint
(цель по времени восстановления 60 с; для крупных баз 60–120 с) размазывает запись ровным фоном.

```sql
ALTER DATABASE [SalesDb]    SET TARGET_RECOVERY_TIME = 60 SECONDS;
ALTER DATABASE [ReportsDb]  SET TARGET_RECOVERY_TIME = 60 SECONDS;
ALTER DATABASE [StatsDb]    SET TARGET_RECOVERY_TIME = 60 SECONDS;
ALTER DATABASE [Legacy2014] SET TARGET_RECOVERY_TIME = 60 SECONDS;
-- проверить:
SELECT name, target_recovery_time_in_seconds FROM sys.databases;
```

Операция применяется на «горячую»; помните: растёт фоновая нагрузка записи — смотрите WRITELOG
в отчёте (сейчас 14 % ожиданий).

## 8. RCSI и ADR (изоляция)

**Несоответствие:** `READ_COMMITTED_SNAPSHOT = OFF` во всех базах; ADR выключен; LCK_M_* — 7 %
ожиданий, блокировки наблюдались в 44 замерах (максимум 11).

**Как по статье** (ч. 2): RCSI по умолчанию OFF во всех версиях, включая 2025 (в Azure SQL — ON).
Платформа 1С 8.3 **сама** включает RCSI в управляемом режиме блокировок; для легаси-конфигураций
(УПП, автоматический/смешанный режим — транзакции на Repeatable Read/Serializable) RCSI бесполезен.
ADR (SQL 2019+) ускоряет восстановление и нужен для «оптимизированных блокировок» SQL Server 2025
(включать вместе с RCSI).

**Действие (по порядку!):** сначала убедиться, что конфигурация 1С переведена на управляемый режим
блокировок; затем включать RCSI:

```sql
ALTER DATABASE [SalesDb] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;
ALTER DATABASE [StatsDb] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;
-- проверить: SELECT name, is_read_committed_snapshot_on FROM sys.databases;

ALTER DATABASE [SalesDb] SET ACCELERATED_DATABASE_RECOVERY = ON;
ALTER DATABASE [StatsDb] SET ACCELERATED_DATABASE_RECOVERY = ON;
```

Помните: версии строк живут в tempdb — см. п. 4 (файлы и размеры tempdb под нагрузкой версионирования).

## 9. Резервное копирование

**Несоответствия:** нет полного бэкапа > 7 дней у ReportsDb (9 дней) и Legacy2014; FULL-модель без
копий журнала у SalesDb и Legacy2014 (`log_reuse_wait = LOG_BACKUP` — журнал SalesDb уже 24 ГБ и
растёт); копии лежат на локальных дисках сервера; шифрования нет; `backup compression default = 0`;
доля ожиданий BACKUPIO 14 %.

**Как по статье** (ч. 2): Full + регулярные копии журнала каждые 15–30 минут; копии хранить **вне
сервера** (сетевое хранилище/S3-холодный архив) + вторая копия; шифрование бэкапов с 2014 (в Express
нет), сертификат хранится отдельно от сервера — иначе бэкап не восстановить.

```sql
-- 1) сжатие по умолчанию
EXEC sp_configure 'backup compression default', 1; RECONFIGURE;

-- 2) регулярная цепочка (в задание SQL Agent; путь — на сетевой ресурс, не локальный диск сервера)
BACKUP DATABASE [ReportsDb] TO DISK = N'\\backup-srv\sqlbackup\ReportsDb_full.bak'
  WITH COMPRESSION, CHECKSUM, INIT, STATS = 10;
BACKUP DATABASE [Legacy2014] TO DISK = N'\\backup-srv\sqlbackup\Legacy2014_full.bak'
  WITH COMPRESSION, CHECKSUM, INIT;
BACKUP LOG [SalesDb] TO DISK = N'\\backup-srv\sqlbackup\SalesDb_log.trn'
  WITH COMPRESSION, CHECKSUM, INIT;
BACKUP LOG [Legacy2014] TO DISK = N'\\backup-srv\sqlbackup\Legacy2014_log.trn'
  WITH COMPRESSION, CHECKSUM, INIT;

-- 3) шифрование копий (сертификат + приватный ключ вывезти с сервера)
USE master;
CREATE MASTER KEY ENCRYPTION BY PASSWORD = N'<сложный пароль>';
CREATE CERTIFICATE SQLBackupCert WITH SUBJECT = N'Шифрование резервных копий';
BACKUP CERTIFICATE SQLBackupCert TO FILE = N'D:\Certs\SQLBackupCert.cer'
  WITH PRIVATE KEY (FILE = N'D:\Certs\SQLBackupCert.pvk',
                    ENCRYPTION BY PASSWORD = N'<пароль ключа>');

BACKUP DATABASE [StatsDb] TO DISK = N'\\backup-srv\sqlbackup\StatsDb_full.bak'
  WITH COMPRESSION, CHECKSUM, INIT,
       ENCRYPTION (ALGORITHM = AES_256, SERVER CERTIFICATE SQLBackupCert);
```

Раз в квартал — учебное восстановление (`RESTORE VERIFYONLY` + восстановление на тестовый сервер).

## 10. Безопасность

**Несоответствия:** смешанный режим аутентификации; `sa` **активна**; 4 SQL-логина, 2 из них —
`sysadmin` (`1C_Admin`, `report_svc`); службы под `NT AUTHORITY\SYSTEM`.

**Как по статье** (ч. 2): не `sa`; службы — доменные учётки/gMSA (вершина — gMSA: пароль генерирует и
ротирует домен); подключение сервера приложений — Windows-аутентификация; права под задачу.
(ч. 1): мгновенное смешивание «всё под sa» — типовая дыра подрядчиков.

```sql
ALTER LOGIN [sa] DISABLE;

-- ревизия привилегированных учёток:
SELECT p.name, p.type_desc, p.is_disabled,
       IS_SRVROLEMEMBER('sysadmin', p.name) AS is_sysadmin
FROM sys.server_principals p
WHERE p.type IN ('S','U','G')
ORDER BY is_sysadmin DESC, p.name;
```

Порядок перехода: создать доменную учётку/gMSA → прописать её в службы SQL Server и Agent →
перевести 1С и служебные задачи на Windows-аутентификацию (или сертификаты для приложений) →
удалить/пересоздать SQL-логины → отключить `sa` → перевести сервер в режим «только Windows».

## 11. Сеть

**Факт:** TCP/IP включён ✅; **именованные каналы включены** ❌ (в отчёте — предупреждение).

**Как по статье** (ч. 2): порт 1433 разрешён **только с адреса сервера приложений 1С**; SQL Browser
(UDP 1434) не нужен — выключить; порт статический; RDP (3389) не публиковать наружу, только через
VPN; именованные каналы выключить.

Действия:
- отключить Named Pipes в SQL Server Configuration Manager → «Протоколы» → именованные каналы →
  «Отключено» → перезапуск службы (или реестр `...\SuperSocketNetLib\Np\Enabled = 0`);
- зафиксировать статический порт (TCP/IP → IP-адреса → TCP-порт 1433/свой), проверить:
  `SELECT DISTINCT local_tcp_port FROM sys.dm_exec_connections WHERE local_tcp_port IS NOT NULL;`
- правило фаервола: 1433 — только с сервера приложений; служба SQL Server Browser — «Отключена»
  (если 1С подключается к именованному экземпляру по имени, укажите в строках подключения
  порт явно или настройте alias через `cliconfg.exe`);
- убедиться, что 3389 не открыт наружу (VPN для админов и подрядчиков).

## 12. Прочее административное

**Query Store** — выключен на StatsDb и Legacy2014; на ReportsDb переведён в `READ_ONLY`
(причина 8 — достигнут лимит размера: 1024 из 1024 МБ). По статье (ч. 2) Query Store — основа
наблюдения: с SQL 2017 в нём есть статистика ожиданий по запросам, с 2022 включён по умолчанию для
новых баз, а восстановленные базы сохраняют старые настройки.

```sql
-- включить, где выключен
ALTER DATABASE [StatsDb]    SET QUERY_STORE = ON
  (OPERATION_MODE = READ_WRITE, QUERY_CAPTURE_MODE = AUTO, MAX_STORAGE_SIZE_MB = 1024, INTERVAL_LENGTH_MINUTES = 60);
ALTER DATABASE [Legacy2014] SET QUERY_STORE = ON
  (OPERATION_MODE = READ_WRITE, QUERY_CAPTURE_MODE = AUTO, MAX_STORAGE_SIZE_MB = 1024, INTERVAL_LENGTH_MINUTES = 60);

-- вернуть из READ_ONLY: увеличить лимит и снять режим
ALTER DATABASE [ReportsDb] SET QUERY_STORE (OPERATION_MODE = READ_WRITE, MAX_STORAGE_SIZE_MB = 2048);

-- контроль: SELECT actual_state_desc, readonly_reason, current_storage_size_mb, max_storage_size_mb
--           FROM sys.database_query_store_options;
```

**Оптимизация ad-hoc** (в отчёте — «Кэш планов засорён ad-hoc запросами»):

```sql
EXEC sp_configure 'optimize for ad hoc workloads', 1; RECONFIGURE;
ALTER DATABASE [SalesDb] SET COMPATIBILITY_LEVEL = 150;  -- ReportsDb 110, Legacy2014 100 — поднять
```

**Мониторинг и ожидания** (ч. 2): мониторинг имеет смысл только для того, кто его интерпретирует —
назначьте ответственного (штатный DBA или внешний специалист); копите историю ожиданий и держите
эталонный снимок спокойного периода. Диагностика одного инстанса ≈ 3 дня — до покупки железа.

## 13. Виртуализация

**Факт:** сервер — виртуальная машина (`virtual_machine_type_desc = VIRTUAL_MACHINE_HYPERVISOR`),
2 сокета × 8 ядер, 2 NUMA-узла.

Проверить на гипервизоре (ч. 1):

| Что | Как правильно |
|---|---|
| Память | Memory reservation (VMware) / без Dynamic Memory (Hyper-V) — SQL Server не должен ждать ballooning |
| ЦП | CPU Ready под контролем, переподписка ~1:1 для СУБД; больше vCPU ≠ быстрее |
| vNUMA | включён и корректно выставлен (CPU hot-add отключал vNUMA до vSphere 8.0.0) |
| Диски | PVSCSI/паравиртуальные контроллеры, несколько контроллеров под разные потоки (данные/журнал/tempdb) |
| План питания | High performance и на хосте, и в гостевой ОС |
| Снапшоты | Долгие снапшоты и гипервизорные бэкапы дают stun (микро-залипания) — согласовать окно |
| Соседи | Датастор не делить с «шумными» ВМ |

## 14. Ожидания: как читать то, что показывает отчёт

Доли из отчёта: PAGEIOLATCH 23 % · CXPACKET 33 % · WRITELOG 14 % · BACKUPIO 12 % · LCK_M_* 7 % ·
RESOURCE_SEMAPHORE 2 % · блокировки в 44 замерах · PLE мин 90 с · CPU пик 97 %.

| Ожидание | Что говорит | Что делать |
|---|---|---|
| `LCK_M_*` | конкуренция за строки/таблицы, длинные транзакции | режим блокировок 1С, RCSI (п. 8), искать head-blocker |
| `CXPACKET` / `CXCONSUMER` | параллелизм: не ошибка, но смотреть связку | cost threshold 25–50, MAXDOP (п. 3); при `PAGEIOLATCH` — индексы |
| `WRITELOG` | не успевает диск журнала | журнал на быстрый отдельный диск (п. 5) |
| `ASYNC_NETWORK_IO` | клиент медленно забирает результат (жадные выборки) | оптимизировать выборки в коде 1С; блокировки держатся, пока клиент не принял результат |
| `PAGEIOLATCH` | не хватает памяти/лишние чтения | память (п. 2), затем индексы/планы |
| `RESOURCE_SEMAPHORE` | кончились гранты памяти на сортировки/хеши | оптимизировать запросы, статистика, память |
| `SOS_SCHEDULER_YIELD` | ЦП-очередь | разбирать топ-запросы по ЦП |

Ожидания безвредные фильтруются, смотрите на **доли и динамику свежим периодом**, а не на список
«плохих типов» — универсального норматива нет.

## 15. План внедрения по приоритетам

**Без остановки сервиса (можно сегодня):**
1. Копии журнала SalesDb/Legacy2014 + полный бэкап ReportsDb → на сетевой ресурс (п. 9).
2. `max server memory`, `MAXDOP`, `cost threshold`, `optimize for ad hoc`, сжатие бэкапов (пп. 2, 3, 12).
3. Отключить `sa`, ревизия sysadmin-логинов (п. 10).
4. `target_recovery_time = 60` на всех базах (п. 7).
5. Query Store: включить/снять READ_ONLY (п. 12).
6. `FILEGROWTH` 512 МБ/1 ГБ вместо 1–2 МБ и 10 % (п. 5).
7. IFI + план питания High performance (п. 6).
8. Отключить именованные каналы, зафиксировать порт (п. 11).

**Окно обслуживания:**
9. RCSI и ADR (после проверки режима блокировок 1С) (п. 8).
10. Пересоздание журнала SalesDb (VLF 1184), добавление 8 файлов tempdb и перенос tempdb на отдельный
    том, перенос файлов между томами (пп. 4, 5).
11. Шифрование резервных копий + вывоз сертификата (п. 9).
12. Lock Pages in Memory (п. 2).

**Инфраструктура / железо:**
13. Вынести tempdb и журнал на быстрые NVMe (write-intensive), разнести потоки по контроллерам (п. 5).
14. Проверить кластер 64 КБ, прогнать DiskSpd и сохранить эталон (пп. 5, 6).
15. Проверить настройки гипервизора (memory reservation, CPU Ready, vNUMA, PVSCSI, снапшоты) (п. 13).
16. Убедиться, что сервер приложений 1С — на отдельной машине, а её рабочие каталоги/Temp — на
    быстрых отдельных дисках (проверяется вручную).

**Ответственный за мониторинг и история ожиданий** — без этого остальное работает вполсилы:
назначить DBA/подрядчика, копить историю, хранить эталонный снимок.
